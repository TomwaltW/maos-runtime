## 1. 这份报告在验什么

复赛交给客户的是一个 zip。客户解压之后会经历什么 —— 双击哪个文件、看到什么、
哪一步会卡住 —— 在 Wave H 之前只被人手工点过，没有任何机器判据盯着。

手工点过的东西有两个问题：**下次没人再点**，以及**点过的人记得的和写下来的不一样**。
所以本轨的产出不是「我点了一遍，没问题」，而是 `scripts/client_smoke.py` ——
一个能反复跑、每条判据都指名道姓的脚本。这份报告是它的第一次真实执行记录。

### 1.1 三条纪律

1. **在解压目录里判，不回仓库取巧。** 客户面对的是一个没有仓库上下文的目录。
   仓库里 `evidence/report.html` 存在，不代表客户包里存在。这条纪律与
   `scripts/make_release.sh` 解压验证那一节同源。
2. **判包的字节，不判解压产物。** Python 的 `zipfile` 既不还原 Unix 权限位、
   又按 cp437 解非 UTF-8 的条目名。可执行位（A2）与文件名编码（W4）两条判据
   因此直接读 zip 头，否则读到的是隔了一层哈哈镜的东西。
3. **跑不了的就写跑不了。** 全局铁律 3 在这一轨的具体形状：Windows 真机行为
   一个字都不声称，静态检查项在输出里打 `[static]` 而不是 `[ok]`。

### 1.2 退出码

沿用 `scripts/ap_smoke.py` 的惯例，理由也一样 —— 整合前「还没装好」是常态，
「装好了但坏了」是事故，两者共用 `exit 1` 就没人看了。

| 退出码 | 含义 |
| :-- | :-- |
| 0 | 全部判据都跑了，全过 |
| 3 | 有前置产物还没并进来，依赖它的判据报「待产出」 |
| 1 | 跑了并且不过 —— 这才是真回归 |

## 3. 判据自验：正反两向的合成夹具

上一节的 15 条「待产出」说明不了判据本身是对的 —— 一个把所有条目都跳过的脚本
也能跑出同样的输出。所以本轨另做了一次**判据自验**。

**这不是客户包的验收。** 夹具是手工合成的两个 zip，不是任何一轨的产出物。
验的是「判据会不会判」，不是「客户包好不好」。探针脚本放在 scratchpad，验完即删，
不入库。

### 3.1 手法

造两个包，除了内容以外形状与约定的客户包一致（四个入口文件在包根、带 `.git`）：

- **正例** `maos-client-good`：每条判据都该过。入口页零外链、相对链接都命中；
  `RUN-ME.command` 带 0755 位，跑起来打印 `RESULT: 10/10 PASS`，藏掉 Python 后
  说人话并指向 `START-HERE.html`；`.bat` 是 CRLF、含 `%~dp0` 与 `py -3`；
  git 历史里没有内部路径。
- **反例** `maos-client-bad`：每条判据都该红。入口页挂两条 CDN 外链、一条断链、
  一条 `/` 开头的绝对路径；`RUN-ME.command` 只有 0644 位、两次跑都吐 traceback
  且从不提 `START-HERE.html`；`.bat` 是 LF、无 `%~dp0`、无 `py -3`；包里留着
  `docs/phases/` 与 `CLAUDE.md`；git 历史里留着一个先提交再删除的 `docs/DECISIONS.md`
  （精确模拟「裁了工作区没裁历史」这种坏法）；包根放一个中文名文件。

### 3.2 结果

| 夹具 | 期望 exit | 实得 exit | 已实测通过 | 静态通过 | 不通过 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| `maos-client-good` | 0 | **0** | 10 | 4 | 0 |
| `maos-client-bad` | 1 | **1** | 1 | 0 | **13** |

反例的 13 条不通过逐条对上了它被做坏的那一处：A2 报 `mode=0644`、A3 报
`CLAUDE.md` 与 `docs/phases/`、A4 报对象库里仍有 `docs/DECISIONS.md`、
B1 报两条 CDN、B2 报断链、B3 报绝对路径、C1 报没有 `RESULT` 行、C2 报吐了
traceback 且没指路、W1–W4 各报各的、D1 报两条死链。

反例里 A1 判为通过是对的：四个入口文件确实都在包根。**入口文件缺席只会变成
「待产出」，不会变成「不通过」** —— 缺文件和文件坏掉是两件事，脚本刻意不把
它们混成一档。

### 3.3 自验顺带捞出的两个自身缺陷

两条都已在 `8b59f8b` 里修掉，写在这里是因为它们都是「不自验就永远发现不了」的那类：

1. **解压不还原权限位，C1 就永远走不到「双击」那条路。** `zipfile.extractall`
   不还原 Unix 权限位，而 macOS 的归档实用工具、Linux 的 `unzip` 都会还原。
   不补这一步，C1 会因为文件没有执行位而静默退回 `bash <file>`，于是 T149 哪天
   把可执行位弄丢了，C1 照样绿 —— 一条永远绿的断言等于没有断言。
2. **W4 判错了对象。** 原先判的是解压后的磁盘文件名，而那串名字已经被 Python
   按 cp437 解过一道。Windows 自带解压器读的是 **zip 条目名 + 通用位标志第 11 位**
   （UTF-8 标志位），判据现在落在那里。

### 3.4 跨会话对齐捞出的第三、四条

2026-09-14，T149 主动发来两个入口脚本的接口约定。其中两条直接指出本脚本会坏在
哪里，都已修掉并各配了对照实验：

1. **入口脚本跑完会暂停等回车**（客户双击时窗口否则瞬间关掉）。macOS 那侧用
   `[ -t 0 ]` 守着 —— stdin 不是 tty 就不暂停。本脚本原先把自己的 stdin 继承给
   子进程，在交互终端里跑会一路挂到超时，然后报一条「客户双击后不会等这么久」的
   **假回归**。已改成 `stdin=DEVNULL`。
2. **成功路径最后一步会用系统默认浏览器真的打开报告页。** 验收脚本每跑一次弹一个
   浏览器窗口是不能接受的。已改成按入口脚本自己的字节探 `--no-open`，探到才传 ——
   这样对不认这个参数的版本同样安全，也不会因为参数名哪天改了就静默失效
   （探不到就是不传，行为回到老样子）。

对照实验：另造一个夹具，无条件 `read`（**不带** `[ -t 0 ]` 守卫）、且没收到
`--no-open` 就 `sleep 999`，配 `--timeout 15` 跑。两条修复任缺其一都会超时：

| 版本 | 耗时 | C1 | exit |
| :-- | :-- | :-- | :-- |
| 修之前 | 15.2s（挂到超时） | 不通过 | 1 |
| 修之后 | 0.4s | 通过 | 0 |

这两条属于**不跨会话对齐就永远发现不了**的那一类：本机此刻跑不到那一步（入口脚本
还没合），等整合期合完再撞上，那一轮验收就会卡在一条假回归上，而查起来像是 T149
的脚本坏了。

### 4.3 做不到就是做不到（本报告永不声称）

本机是 macOS，下面这些**没有任何办法在本机产生真实读数**，任何关于它们的结论
都只能来自一台真 Windows 机器：

- Windows 自带解压器（资源管理器「提取全部」）会不会吞掉可执行位、会不会

- GBK 控制台下中文提示的实际显示效果，以及 `chcp 65001` 之后的行为。
- `py -3` 在**没装** Python launcher 的机器上的实际落点，以及 `python` 撞进
  微软商店 stub 时的表现。
- 双击 `.bat` 时 SmartScreen / 组策略的拦截行为。

## 5. 发现的别轨问题

按派单 §4.3，本轨是验收方，**发现即报告，不自己动手改**。

### 5.1 密钥自查误报，堵死打包（高）

`scripts/make_release.sh` 在当前主干上 **exit 1**，卡在最后一步「密钥自查」的
B 层（已知密钥形态正则）：

```text
==> 密钥自查
    [ok]   哨兵反查: 0 命中（本机敏感变量的值都没进包）
    [FAIL] 密钥形态命中 1 个文件：
```

命中的是 `maos/tests/test_model_routing.py` 第 37 行 —— 一个**明确标注为假**的
测试夹具，它自己的注释原文就是「故意构造的假 key，只在第 4 组用例里出现。
它不是任何真实凭证」。B 层的 `sk-[A-Za-z0-9]{20,}` 正则命中了它。

这行不是本波引入的：`git log -S` 指向 `38eca1a`（2026-09-01，Phase 9 的角色→模型
路由表）。也就是说 **`make_release.sh` 从 9-01 起就打不出一个 exit 0 的包**，
而这件事在本轨之前没有任何判据盯着 —— 打包脚本平时没人跑，跑的时候也没人看退出码。

**为什么算高**：复赛要交的就是这个包。A 层哨兵反查（拿本机环境变量真值反查）
是 0 命中的，所以**没有真实密钥泄露**；坏的是这道闸本身 —— 一道永远红的闸，
人只会学会绕过它，于是它哪天抓到真东西也没人信。

**归属 T150**（它正在改 `make_release.sh`）。建议方向二选一，不在本轨拍板：
给 B 层加一个「文件内已声明为假夹具则豁免」的口径，或把假 key 的字面量拆成
运行时拼接、让它不再长成密钥形态。

### 5.2 `--zip` 模式下包的种类判错（中，已在本轨修）

`client_smoke.py` 早期版本里，`--zip` 指定的包算不算客户包，是靠**本仓库的**
`make_release.sh` 支不支持 `--client` 来答的。整合期从别的轨手上接一个包过来验时，
这答的是另一个问题。已加 `--kind client|internal|auto`，缺省仍是 auto。
记在这里是因为它会影响整合期怎么用这个脚本。
