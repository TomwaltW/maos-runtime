§0

这份材料证明什么

读法
先说清楚这份材料证明什么、不证明什么 —— 边界不划清，后面每一个数字都可以被读成别的意思。
✓ 这份材料证明① 八条链路各自真的从头跑到了终态，中间每一次状态变化都在库里有行；
② 每个 Skill / ToolPort 调用都留了 input_digest 与 output_hash，与事件日志逐条对得上；
③ 判「业务成功」的依据是外部权威判据（沙箱 pytest 报告 / 支付网关回执），不是 Agent 自己说完成了；
④ 这些结论可以被外人独立重放 —— 核验器八项逐项 PASS，任一项失败都说得出失败意味着什么。
✕ 这份材料不证明① 不证明业务数据是真实客户数据 —— 政策与历史案例是按行业惯例构造的合成数据，支付网关的错误码与时序取自公开规范；
② 不证明模型效果 —— 缺省路径用 ScriptedModelClient，token 数是估算，只能读作调用规模；
③ 不证明退款真的到账 —— 权威在支付网关，MAOS 只持有观察与推断；
④ 不证明性能 —— 八条链路合计 5947 ms 是确定性复现的耗时，不是压测结论。

§1

验证方法

方法
检索不准顶多说效果一般；无法核验就是零分。所以每一项判据都必须能被外人独立跑一遍，且失败时说得出失败意味着什么。

§1.1两条命令，缺一不可

$ python3 scripts/make_evidence.py   # ① 跑 7 个场景 + RAG 对照，产 evidence/scenario-1..7 与 -R5
$ python3 scripts/verify.py          # ② 八项证据逐项重放校验 → RESULT: 8/8 PASS
为什么不能只跑第 ② 条：*.db 不入 git（被 .gitignore 挡着），核验器要的是库、不是快照。直接跑 ② 会报「缺数据库」并退出 2 —— 这是设计行为，不是坏了。全新克隆实测 clone + 两条命令共约 7 秒。

§1.2八项判据分别在防什么

#判据校验什么这一项失败意味着
1hash-integrity每个 skill / tool 调用的 input_digest、output_hash 与 event_log 一致证据被篡改，或事后手写
2business-ref每条 business_ref 指向的对象在库中存在且 version 匹配引用悬空 —— 业务锚点是假的
3authoritative-fact每个 settled 都有对应 payment_observation，且 actor_invocation_id 属于 payment.observe权威事实边界被绕过
4trace-treetrace.json 的 span 树无孤儿、无环，且与库重放逐字节一致事件链不完整
5kb-hit每个 KbRetrieved 的 doc_id 在 kb_doc 中存在RAG 命中是编的
6business-outcome每个 Plan 终态都有 business_outcome；DONE 必须有外部判据，且那条判据能在库里回查得到「Agent 都完成了」被当成业务成功
7history-case本库晋升的 history_case 都能追溯到 outcome=success 的真实 case知识层被污染
8cost-attribution每条 model_usage 都挂得到 plan 的 trace_id、task_id 回查得到，estimated 标记与 model 列相符成本归因是假的，或估算被印成了真实计费

§1.3三种结论与退出码

结论进不进分子什么时候出现退出码
[PASS]进该项有可判对象，且全部通过0（全 PASS 时）
[FAIL]进（记为不通过）有对象且判不过 —— 逐条点名，不给汇总糊过去非 0
[SKIP]不进上游能力没落地，或该项分母为 0（空转）不单独影响
不许静默跳过一个 7/7 里藏着两个没跑的，比老老实实写 5/5 PASS + 2 SKIP 更坏 —— 后者看得出没跑。
空转也算没跑0/0 PASS 与「真跑了且全过」在屏幕上长得一模一样。这是核验器能犯的最坏的错，所以专门做了 _idle_skip 挡它。
依赖方向核验器不 import maos/domain/** 的业务逻辑，只按「表在不在」决定某一项跑还是 SKIP —— 换一个业务域，这八项一行都不用改。
