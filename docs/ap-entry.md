# 供应链付款入口 —— 把你自己的付款数据放进去

系统里管应付账款的那条流程（三单匹配 → 付款计划 → 等人批 → 发付款指令 →
问银行要回单）**早就跑通了**，缺的一直是一条通道：你手上那份付款数据
（一张表，或者一叠发票图片）怎么进去。这篇讲的就是这条通道。

上半给不写代码的人看，下半给评委看。两半讲的是同一件事的两面：
**怎么用**，和**为什么是这个用法**。

---

## 上半：给业务方

### 一、我要准备什么：两份东西，一份配一次，一份每天给

| | 底账 | 申请表 |
| :-- | :-- | :-- |
| 谁给 | IT / 顾问 | 你（财务、采购、应付岗） |
| 多久给一次 | **配一次**，之后不用天天动 | **每天给** |
| 里面是什么 | 供应商、采购订单、收货记录 | 今天要付的这几张发票 |
| 哪来的 | 从 ERP 导出 | Excel 填好，存成 CSV |

**底账**是外部系统的事实：这家供应商的银行账号、付款条件，这张采购单订了多少、
单价多少，仓库那边实际收到多少、退回多少。这些不该让你每天手抄一遍 ——
抄错一次，匹配结论就错一次，而且不会有人发现。

**申请表**里你只填**发票上真实印着的东西**：一行一个发票行项目，同一张发票有几个
明细行就写几行（这就是 Excel 里发票明细表本来的样子）。

| 你要填的列 | 说明 |
| :-- | :-- |
| 发票号 | 这是唯一那把钥匙 |
| 采购单号 | 这张票对应哪张采购单 |
| 行号 / SKU | 发票明细的第几行、什么货 |
| 发票数量 / 发票单价 | 票面上印的数 |
| 开票日期 / 到期日 / 税率 | 票面上印的日期与税率 |
| 说明 | 随便写，给人看的 |

**供应商是谁、币种是什么、订单订了多少、仓库收了多少 —— 一概不用填**，
发票号和采购单号一填，全部从底账里查出来。

同一张发票的几行，采购单号、开票日期、到期日、税率必须一致。不一致会**当场报错**，
不会挑第一行、也不会按多数派来。两行写着不同的到期日，说明表填错了，
不是让系统替你选一个。

### 二、发票是图片怎么办：多走一道人工复核

拍照或扫描的发票也能进，但**不是直接进付款**，中间隔着一道你必须过的关：

```text
发票图片  →  自动抽取（把票面读成字段）
              →  生成一张【待复核表】
                   →  你逐行核对，把「需人工确认」从「是」改成「否」
                        →  这时才转成正式申请表，进付款
```

待复核表和你自己填的申请表**长得一模一样**，只多两列：`来源`（这行是从哪张图片
读出来的，出了事回去看原件）和 `需人工确认`（是 / 否）。

🔴 **只要还有一行写着「是」，付款入口会拒绝整张表。** 这不是麻烦你，
理由写在下半第一节 —— 一句话：看错一个小数点，就是多付一笔钱。

### 三、我会拿到什么：一张中文表

跑完给你一张中文结果表，每张发票一行，告诉你四件事：

| 这一列回答 | 你关心的问题 |
| :-- | :-- |
| 匹配过没过 | 票、单、货三方对得上吗 |
| 差在哪 | 对不上的话，是数量差、单价差、还是税额差，差多少 |
| 停在哪、等谁批 | 卡住了的话，是卡在什么闸上，等哪个角色放行 |
| 钱到没到账 | 付款指令发出去之后，银行到底回没回执 |

这张表的形状，与退款那条通道已经在用的完全一致。下面是**退款域**入口
2026-09-02 在本工作区的真实输出，供应链付款那张表照这个样子读：

```text
订单号         诉求        裁定  核准金额  退款状态    依据                         转人工
ORD-2026-0001  质量问题    批准  6800.00   已到账      按基线（命中 3 条售后规则）  1
ORD-2026-0002  七天无理由  驳回  0.00      未发起退款  AS-001@v1                    0
ORD-2026-0003  质量问题    批准  24000.00  已到账      按基线（命中 3 条售后规则）  1

共 3 单：批准 2、驳回 1；已到账 2 单合计 30800.00 元；期间 2 次停下来等人放行。
```

最后那句「期间 2 次停下来等人放行」要特别说一下：**停下来等人不是出故障**。
真要把钱付出去的那一步风险最高，闸放行了也照样停住等主管点头 ——
系统只负责把该看的都摆到人面前，按不按那个钮是人的事。

### 四、现在能跑到哪一步

这条通道分四块并行在建：表格入口、票据抽取、复核关口，以及本文这份文档与冒烟。
本文落盘时，前三块还没并进来。

仓库里的冒烟脚本 `scripts/ap_smoke.py` 会自己探：三块都在就跑一遍完整流程；
缺哪块就告诉你缺哪块，然后以 **exit 3** 退出（不是 1）——
「还没装好」和「装好了但坏了」要分得开，脚本里、人眼里都得分得开。

## 下半：给评委

### 一、为什么抽取结果不能直接进付款

因为读票的那个模型，**名字里就写着它是实验版**。

2026-09-02 实测网关上可用的模型清单是三个：两个文本模型，加一个
`deepseek-v4-flash-vision-exp` —— 抽发票只能用这一个，而结尾那三个字母是
experimental。（模型清单为编排侧当日实测，本轨未复跑，不出网。）

拿一个实验版视觉模型去读票面，它会看错。看错的不是抽象的「准确率」，
是很具体的一件事：**小数点的位置**。`1250.00` 读成 `12500.0`，
金额差十倍；`0.13` 的税率读成 `0.18`，税额对不上。这两种错在待复核表上，
人扫一眼就能发现；直接进付款，钱就划出去了。

所以设计上留了一道**不可绕过**的关：抽取的产出只能落成待复核表，
人逐行确认之后才转正式申请表，付款入口拒绝任何还带着「需人工确认」的行。

这不是对模型能力的悲观估计，是**授权边界**的划法 —— 见下一节。

### 二、与铁律 8 的关系：理解可以错，授权不许错

铁律 8 说的是：MAOS 不持有权威事实，只持有观察与推断。订单、支付、库存的
权威状态永远归属外部系统。

抽取这件事是它在**自然语言层**的同一句话。模型读票，产出的是**推断**，
不是事实 —— 票面上到底印着多少，权威在那张纸（和开票系统）那里，不在模型的
输出里。所以推断可以进系统，但只能以「待确认」的身份进；把它升格成「事实」的
那一步，必须由人来做。

一句话概括这条设计取向：

> **理解可以错，授权不许错。**

模型理解错了，人在复核表上能改回来，代价是几分钟；授权错了，钱已经出去了，
代价是一笔货款和一场对账。两种错的**可逆性根本不在一个量级**上，
所以它们不能共用同一道关。

同一句话在流程末端还有一个对称的落点：付款指令发出去之后，
银行的回单问不出来时，系统**一个字都不写** —— 不推状态、不落观察行。
「我问累了」和「银行说没付成」是两回事，把前者写成后者，账面上就会凭空少一笔，
而供应商那边其实收到了钱。这条已经在引擎里跑了很久，本轮一行没动。

### 三、为什么不做模糊匹配

发票上的采购单号读成 `PO-2026-000l`（小写 L），底账里是 `PO-2026-0001`（数字一）。
只差一个字形，模糊匹配会「体贴地」帮你把它归到那张单上。

问题是：**这两个字符串在业务上是两张不同的单子**，可能属于两个不同的供应商。
猜对了，省了人一次输入；猜错了，钱付给了另一个供应商 —— 而这笔付款
全程没有任何一处会变红，因为系统认为自己匹配成功了。

所以口径是**认不出就报错，并列出可选项**，一个字都不猜。这与退款域那条通道
认「诉求类型」的口径是同一条：写不在表里的词当场报错。猜错一个词，
套用的就是另一条政策；猜错一个单号，付的就是另一家的账。

代价是人偶尔要多填一次。这个代价我们认。

### 四、引擎为什么一行没改

`maos/flows/scenario_10.py` 是应付账款域的完整流程 —— 三单匹配（数量、单价、
税额各自容差）、出付款计划、高风险任务停在 `BLOCKED` 等人批、发付款指令、
轮询回单、问不出终态就开对账工单补偿。本轮**一行没改**，
它的五个测试文件 120 条用例（2026-09-02 在本工作区复跑）也一条没动。

换一个业务域要换的只有两样：**入口**（数据怎么进来）和**数据**（底账与申请表），
流程、状态机、契约一概不动。这正是铁律 9 要的东西：业务状态是业务对象自己的
字段，不是 Task 状态。应付账款的 `compensated`、退款的 `settled`，
都写在各自的业务对象上，`maos/contracts/states.py` 里一个新状态、
一条新迁移都没加。

反过来讲，这条也是这次改造能不能算数的判据：如果接一个新业务域必须动状态机，
说明抽象错了 —— 那就该停下来重新设计，而不是给状态机多加两个格子。

三单落库也只走一条路：`maos/domain/ap/fixtures.py` 里那对函数。
不许写第二条构造路径 —— 两条路径一定会漂，而漂的那天没有任何东西会变红。

### 五、这条通道与退款那条是同一个形状

退款域的入口（底账 `scenarios/custom/ledger.json` + 一张申请表 CSV，
流程在 `maos/flows/custom_case.py`，入口在 `scripts/run_requests.py`）
是先趟通的那条。供应链付款这条**照它的形状复刻**，不是另起炉灶：

| | 退款域 | 供应链付款域 |
| :-- | :-- | :-- |
| 配一次的东西 | 底账：客户 / 渠道 / 商品 / 订单 / 政策 | 底账：供应商 / 采购订单 / 收货记录 |
| 每天给的东西 | 退款申请表，一单一行 | 发票申请表，一个明细行一行 |
| 人只填 | 订单号 + 诉求类型 | 发票号 + 采购单号 + 票面数字 |
| 其余字段 | 按订单号从底账查 | 按发票号 / 采购单号从底账查 |
| 认不出的词 | 当场报错，列出可选项 | 当场报错，列出可选项 |
| 拿到什么 | 一张中文结果表 | 一张中文结果表 |

两条通道的差别只有一处：供应链付款多了**图片进件**这条支路，
于是也就多了那道人工复核关。
