# PolarDB PostgreSQL 版 —— 真连实测记录

这份文档只回答一个问题：**MAOS 的 PG 通道要用到的能力，在一台真实的
PolarDB PostgreSQL 版实例上，到底哪些是跑过的、哪些没跑过。**

它存在的理由是：材料里关于 PolarDB 的说法此前只有一句**推理** ——
「PolarDB 兼容 PG 协议 + pgvector 扩展可用，所以能跑」。推理不是实测。
本文件负责把那句话换成一条一条可复核的记录，**包括没跑通的那些**。

## 一、已实测

### 1.1 对照组：本机 Docker pgvector —— 五步全绿 ✅

**这一栏不是 PolarDB 的结论**，它的作用是排除「脚本本身有问题」这个可能：
先在一台已知可用的库上跑绿，之后连 PolarDB 再失败，才能归因到 PolarDB。

- 环境：`pgvector/pgvector:pg16` 容器（`deploy/docker-compose.yml` 的 `pg` profile）
- 命令：`python3 scripts/polardb_smoke.py --local`
- 结果：**5/5 步通过，exit=0**

```

====================================================================

  [ OK ] 3. 全文 to_tsvector + ts_rank -> 命中 ['d1']，ts_rank=0.099103（越大越相关）
  [note]    （观察）中文 to_tsvector('simple') -> '退款订单已经超时未处理':1
  [ OK ] 4. 向量 vector 列 + <=> 排序 -> top-1=a，余弦距离 a=0.000000, c=0.006116, b=1.000000（越小越相关）
```

五步各自验的是什么，以及断言强度：

| # | 验什么 | 断言（不是「没报错就算过」） |
| :-- | :-- | :-- |
| 1 | 连接 + `SELECT version()` | 拿到版本串 |
| 2 | `CREATE EXTENSION IF NOT EXISTS vector` | 且能从 `pg_extension` 读出 `extversion` |
| 3 | `to_tsvector` + `ts_rank` | 命中集合**必须恰好等于** `['d1']`（`fox & brown` 只有 d1 同时含两词），且 `ts_rank > 0` |
| 4 | `vector` 列 + `<=>` + 排序 | 构造已知相似度，**全序必须恰好等于** `['a','c','b']` |
| 5 | 清理 | 两张自建表删净，不留垃圾 |

### 1.3 前置条件：普通账号跑不完这五步（第一次 2/5 的实录）

控制台建的**普通账号**连上去，第 2、3 步当场挂掉：

```
  [ OK ] 1. 连接 + SELECT version() -> PostgreSQL 16.14 (PolarDB 16.14.20.0 build 1f03f15d) on x86_64-linux-gnu
  [FAIL] 2. CREATE EXTENSION vector -> InsufficientPrivilege: permission denied to create extension "vector"
            HINT:  Must be superuser or user with all of polar_superuser to create this extension.
  [FAIL] 3. 全文 to_tsvector + ts_rank -> InsufficientPrivilege: permission denied for schema public
  [FAIL] 4. 向量 vector 列 + <=> 排序 -> 跳过：第 2 步没拿到 vector 扩展
  [ OK ] 5. 清理临时表 -> maos_smoke_fts / maos_smoke_vec 已删
结论：2/5 步通过   exit=1
```

**这是两个互相独立的坑，别当成一件事**（只修其中一个，另一个照样挡住）：

| 症状 | 根因（实测） | 修法 |
| :-- | :-- | :-- |
| 装不了 `vector` | 普通账号 `rolsuper=f` 且不属于任何角色；PolarDB 要求 `polar_superuser` | 控制台「账号管理 → 创建账号 → **高权限账号**」，用它执行一次 `CREATE EXTENSION` |
| `public` 里建不了表 | PG15 起 `public` 的 ACL 是 `{pg_database_owner=UC/pg_database_owner,=U/pg_database_owner}`，普通用户只有 `USAGE` 没有 `CREATE`；且本库 owner 是 PolarDB 内建的 `aurora`，普通账号对库也没有 `CREATE`，**连自建一个模式绕开都不行** | 高权限账号执行 `GRANT CREATE ON SCHEMA public TO <普通账号>` |

高权限账号跑完这两条 DDL 之后，**后续全程用普通账号**即可 —— 灌 schema、跑测试都不再需要高权限。

账号盘点（实测 `pg_roles`）：`aurora` / `polardb_admin` / `replicator` 三个是 PolarDB
**内建**超级用户，口令不归使用者掌握，**别指望用它们**；控制台新建的高权限账号属于
`pg_polar_superuser` 角色，这才是能用的那个。

### 1.4 中文分词：zhparser 在 PolarDB 上装成了，中文真的切开了

`deploy/polardb.md` 原先推断「托管实例大概率装不了中文分词扩展」。上一轮只验到
「在可用扩展列表里」，**这一轮把它装了**：

```
CREATE EXTENSION zhparser                                      -> zhparser 2.2   (0.03s)
CREATE TEXT SEARCH CONFIGURATION zhcfg (PARSER = zhparser)     -> OK             (0.01s)
ALTER TEXT SEARCH CONFIGURATION zhcfg ADD MAPPING FOR n,v,a,i,e,l WITH simple    (0.01s)
```

同一句话，两个配置的分词结果：

```
simple  ->  '退款政策超时未到账':1                      ← 整句一个 token
zhcfg   ->  '退款':1 '政策':2 '超时':3 '到':4 '账':5     ← 真切开了
```

装扩展要高权限账号（与 `vector` 同理，见 §1.3）；**建配置之后普通账号不用任何授权
就能用 `zhcfg`**，配套的 GIN 索引也由普通账号建（表是它建的，它是 owner）。

#### 召回实测：24 条真语料，三条通道对比

语料是 `scenarios/refund/history/`（24 条历史案例，真中文），
灌进 `kb_doc_pg` 并用 `maos/kb/retriever.py` 的 `embed()` 现算 64 维向量。
「应命中」由标题人工核定，不是事后凑的。

| 查询 | 应命中 | `simple` 全文 | `zhcfg` 全文 | 向量通道 top-3 |
| :-- | :-- | :-- | :-- | :-- |
| 无理由退货 | 0001, 0009 | 抛 `LookupError` | **0009, 0001** | 0001, 0009, 0012 |
| 余额不足 | 0019 | 抛 `LookupError` | **0019** | 0019, 0002, 0010 |
| 人为损坏 举证 | 0008, 0016 | 抛 `LookupError` | **0016, 0008** | 0016, 0008, 0009 |
| 调用频次超限 | 0018 | 抛 `LookupError` | **0018** | 0018, 0020, 0017 |
| 折旧 | 0014 | 抛 `LookupError` | **0014** | 0003, 0011, 0012 |
| 渠道商核销 | 0003, 0011, 0015 | 抛 `LookupError` | 0003 | 0003, 0011, 0012 |

**合计：`zhcfg` 全文 8/10，向量 top-5 10/10，`simple` 一条都查不了（全部抛错）。**

三条结论，各自的依据都在上表里：

1. **装 zhparser 把中文全文通道从「完全不可用」变成「可用」。** `simple` 那一列六条
   全是抛错 —— 不是召回差，是这条通道压根走不通（`_port_search` 一次 CJK 查询就把
   它永久标记不可用，见 `polardb.md`）。
2. **`zhcfg` 漏的那两条是 `plainto_tsquery` 的 AND 语义，不是分词的锅。**
   「渠道商核销」被切成 `渠道商 & 核销`，而 0011／0015 的原文是「经销渠道…核销」，
   没有「渠道商」这个词，AND 下必然不命中。全文通道对同义词无能，这是它的本性。
3. **两条通道互补，不是替代关系。** 向量 top-5 全中（同义词靠语义捞回来），但排序噪声大
   ——「折旧」这条的前 3 名全错，正确答案在第 4-5 名；而 `zhcfg` 把它排在第 1。

### 1.5 HNSW 向量索引：规模性能与召回

数据是**合成**的（真语料的 210 条句子随机重组），向量走的是真实的 `embed()`，
所以向量分布是这套系统的真实分布，不是随机噪声。🔴 **这一栏的数字来自合成数据，
不要当成真业务负载的结论** —— 真语料只有 24 条，撑不起规模测试。

时间一律取 `EXPLAIN (ANALYZE)` 的服务端 `Execution Time`，**不含公网往返**
（家宽到北京 RTT 几十毫秒，会把 0.5ms 的差别整个淹掉）。查询 30 条，与库内文档同分布。

| 规模 | 通道 | 计划 | p50 | p95 | 召回@10 | 相对顺序扫描 |
| :-- | :-- | :-- | --: | --: | --: | --: |
| **5 万行** | 顺序扫描（精确解） | Seq Scan | 16.1 ms | 17.6 ms | — | 1.0x |
| | HNSW `ef_search=10` | Index Scan | 0.29 ms | 0.39 ms | 89.7% | 56x |
| | HNSW `ef_search=40`（缺省） | Index Scan | 0.58 ms | 0.82 ms | **99.3%** | 28x |
| | HNSW `ef_search=100` | Index Scan | 1.06 ms | 1.43 ms | 99.7% | 15x |
| | HNSW `ef_search=400` | Index Scan | 2.80 ms | 4.16 ms | 99.7% | 6x |
| **20 万行** | 顺序扫描（精确解） | Seq Scan | 72.5 ms | 79.8 ms | — | 1.0x |
| | HNSW `ef_search=10` | Index Scan | 0.33 ms | 0.53 ms | 85.0% | 220x |
| | HNSW `ef_search=40`（缺省） | Index Scan | 0.62 ms | 0.86 ms | **99.3%** | 117x |
| | HNSW `ef_search=100` | Index Scan | 1.19 ms | 1.70 ms | 99.7% | 61x |
| | HNSW `ef_search=400` | Index Scan | 3.87 ms | 4.62 ms | 99.7% | 19x |

构建与体积（`m=16, ef_construction=64`，pgvector 0.8.3.1 的缺省值，未调参）：

| 规模 | 建索引耗时 | 索引大小 | 堆表 | COPY 入库（含公网传输） |
| :-- | --: | --: | --: | --: |
| 5 万行 | 8.7 s | 27 MB | — | 23.6 s（2122 行/秒） |
| 20 万行 | **77.9 s** | 109 MB | 123 MB | 198.1 s（757 行/秒） |

四条结论：

1. **HNSW 的查询延迟几乎不随规模增长**：数据涨 4 倍（5 万 → 20 万），`ef_search=40`
   的 p50 从 0.58ms 只到 0.62ms；而顺序扫描从 16.1ms 涨到 72.5ms（线性）。
   所以**加速比随规模放大**：28x → 117x。这是建这条索引的全部理由。
2. **建索引耗时是超线性的**：数据 4 倍，耗时 9 倍（8.7s → 77.9s）。10 倍数据时别按
   线性估工期。
3. **索引不小**：109 MB 索引 vs 123 MB 堆表，接近 1:1。64 维尚且如此，换更高维的
   嵌入模型要重新算存储账。
4. 🔴 **`ef_search=10` 不要用**：召回 85%–90%，而且**不稳定** —— 同一份数据、同一组
   查询，换一次索引构建就能从 100% 掉到 89.7%（本轮实测到过这个跨度，见 §3.6）。
   `ef_search=40`（pgvector 缺省）在两个规模上都稳定在 99.3%，延迟只有 0.6ms，
   **没有理由往下调**。

## 三、已知差异 / 局限

### 3.1 中文分词：PG 自带分词器不切中文（本机实测现象）

第 3 步的观察项实测到：

```
to_tsvector('simple', '退款订单已经超时未处理')  ->  '退款订单已经超时未处理':1
```

**整句被当成了一个 token**（`:1` 是它的位置），没有任何切分。
这不是配置错误，是 PG 默认分词器不认中文 —— 换 `'english'` 配置结果同理。

其后果是：**中文语料上的全文检索基本只能命中「整句完全一致」的查询**，
`ts_rank` 的排序在中文上不具备可用的区分度。

同一条在 **PolarDB 上复测，现象完全相同**：

```
to_tsvector('simple', '退款政策超时未到账')  ->  '退款政策超时未到账':1
```

> 🔴 **口径以 T10 的 `deploy/polardb.md` 为准，本文件只出现象、不下结论。**
> 常见的三条出路（装 `zhparser`／`pg_jieba` 扩展、应用层预分词后写入、
> 全文通道只用于英文与 ID 类字段而中文走向量通道）各自的取舍属于 T10 的面。

**但这条局限在 PolarDB 上是可解的** —— `deploy/polardb.md` 当时推断「托管实例大概率
装不了中文分词扩展」，实测推翻了：可用扩展列表里四个都在，且 `zhparser` **已经装上并
实测通过**（§1.4）。

| 扩展 | 可用版本 | 本轮是否安装 |
| :-- | :-- | :-- |
| `zhparser` | 2.2 | ✅ **已装并实测**，见 §1.4 |
| `pg_jieba` | 1.1.2 | 否（在可用列表里） |
| `pg_bigm` | 1.2 | 否（在可用列表里） |
| `pgroonga` | 4.0.5 | 否（在可用列表里） |

所以 §3.1 这条局限的准确表述是：**PG 内置配置不切中文，这一点在 PolarDB 上同样成立；
但 PolarDB 允许装 `zhparser`，装完这条局限就解除了**。未装的那三个仍然只验到
「在可用列表里」，没装过。

### 3.2 PolarDB 与本机 pgvector 的行为差异 —— 检索行为零差异，差异在别处

**五步里的每一个数值逐字节相同**（左：本机 Docker `pgvector/pgvector:pg16`；
右：PolarDB 16.14）：

| 项 | 本机 pgvector | PolarDB | 差异 |
| :-- | :-- | :-- | :-- |
| 全文命中集 | `['d1']` | `['d1']` | 无 |
| `ts_rank` | `0.099103` | `0.099103` | 无 |
| `<=>` 全序 | `a, c, b` | `a, c, b` | 无 |
| 余弦距离 | `0.000000 / 0.006116 / 1.000000` | `0.000000 / 0.006116 / 1.000000` | 无 |
| 中文 `to_tsvector('simple')` | 整句一个 token | 整句一个 token | 无（见 §3.1） |

差异全在检索行为之外的这三条：

| 项 | 本机 pgvector | PolarDB | 影响 |
| :-- | :-- | :-- | :-- |
| pgvector 版本 | 0.8.6 | **0.8.3.1**（旧两个小版本） | 本层只用 `vector` 类型与 `<=>`，两版实测无差 |
| PG 版本串 | `16.15 (Debian ...)` 社区版 | `16.14 (PolarDB 16.14.20.0 build 1f03f15d)` | 版本串本身就是「这是不是真 PolarDB」的判据 |
| 权限模型 | 容器里的账号是 superuser，五步随便跑 | 普通账号跑不完，需高权限账号先做两条 DDL | 见 §1.3 —— **这正是本机对照组测不出来的那一类问题** |

### 3.3 分数方向：两个通道相反，接 StorePort 时必须转换

本机实测到的方向（PolarDB 上预计相同，但**未实测**）：

| 通道 | 算子 | 原始值方向 | 实测样例 |
| :-- | :-- | :-- | :-- |
| 全文 | `ts_rank(...)` | **越大越相关** | 命中 d1 → `0.099103` |
| 向量 | `<=>`（余弦距离） | **越小越相关** | `a=0.000000, c=0.006116, b=1.000000` |

契约 F-2 附则要求两个后端的 `fts_search` / `vector_search` 都返回
**「越大越相关」** 的分数。所以向量通道在实现侧必须做一次方向翻转
（例如 `1 - (embedding <=> query)`），**否则排序会整个倒过来，而两边的测试
各自都可能是绿的** —— 这属于 T10 实现面的事，此处只记录方向差异这个事实。

### 3.6 HNSW 低 `ef_search` 的召回随索引构建波动 —— 一条测量过程本身的教训

本轮 §1.5 那张表里 `ef_search=10` 的召回是 89.7%（5 万行）／85.0%（20 万行）。
但中途有三次独立测量在**同一份数据、同一组查询**上拿到 100%。差别只有一个：
那三次用的是**上一次构建出来的索引**，而最终表里的数字来自 `DROP INDEX` 后
**重新构建**的索引。

结论：**低 `ef_search` 下，召回率是「这一次索引怎么建出来的」的函数，不是数据的函数。**
HNSW 的构建有随机性，图的连通性每次不同，低 `ef` 的贪心搜索对此敏感；
`ef_search ≥ 40` 时两个规模、多次构建都稳定在 99.3%–99.7%。

这条之所以写进文档，是因为它差点变成一个错误结论：中间那三次 100% 如果先出现、
且没有重建索引再验一遍，就会得到「HNSW 在这个规模上无损」这个**过于漂亮而错误**的结论。
凡是「换一次构建就变」的数字，单次测量都不算数。

### 3.5 SSL：从「不支持」到已开启（含开启前的明文期实录）

🔴 **口令未轮换 —— 明文期的暴露没有被撤销**，见本节末尾「未闭环」。

#### 开启前（2026-08-30 实测）

实测（客户端侧 libpq 的判定 + 服务端参数，两边互相印证）：

```
sslmode=prefer   ✅ 连上，客户端侧 SSL 生效 = False
sslmode=require  ❌ OperationalError: server does not support SSL, but SSL was required
SHOW ssl                  -> off
SHOW password_encryption  -> md5
```

`sslmode=prefer` 是 libpq 的**缺省值**，语义是「能加密就加密，**不能就明文连**」——
所以 DSN 里不写 `sslmode` 时不会有任何提示，连接照常成功，你不会知道它没加密。

口径要分清，别把话说过头：

- 口令**不是**明文过线 —— `password_encryption = md5`，走的是挑战应答，线上传的不是原文口令；
- 但 **查询语句与查询结果全程明文**，且 md5 认证本身早已不足以对抗离线爆破；
- 这是一条**公网**链路，中间人可读可改。

#### 开启后（2026-08-31 实测）

控制台侧已开启 SSL 加密，两个 DSN 都已带 `?sslmode=require`。实连回执：

```
（普通账号 polardb_maos，pg.env）
服务端 ssl 参数 : on
本连接走 SSL   : True

（高权限账号 maos_admin，pg-admin.env）
current_user   : maos_admin
服务端 ssl 参数 : on
本连接走 SSL   : True
```

验证方式是两边互相印证：服务端读 `show ssl`，客户端读 `c.pgconn.ssl_in_use`。
**只看其中一个都不够** —— 服务端 `on` 只说明它支持，不说明你这条连接真的用上了；
`sslmode=prefer` 下服务端照样是 `on` 而连接是明文，这正是开启前那一段的情形。

`require` 只加密不验证证书；要验证书就 `verify-ca` 并配 `sslrootcert`，本轮没做。

`pg-admin.env` 那条是**后补的**：开 SSL 那一轮的派单只写了改 `pg.env`，高权限账号
那条漏了，于是出现「实例侧 SSL 已开、`maos_admin` 仍走 `prefer`」的半吊子状态 ——
加密开着，但那条连接能明文就明文。2026-08-31 补齐并实连验证。
**这类缺口不会报错，只会安静地不生效**，和 `prefer` 本身的毛病是同一个。

#### 🔴 未闭环：口令没有轮换

开启 SSL 之前，这两个账号的口令在上面那条**明文公网链路**上用过多次。「按已暴露处理」
是当时就写下的结论，现在仍然成立 —— **开 SSL 不能追溯地保护开之前的流量。**

已决定不轮换（见 `docs/DECISIONS.md`）。这是**接受风险**，不是消除风险：

- 加密只对开启之后的连接生效；开启之前跑过的东西，该被看到的已经被看到了；
- `password_encryption = md5` 意味着线上传的不是原文口令，但 md5 早已不足以对抗
  离线爆破 —— 抓到过那几次握手的人，有离线还原的空间；
- 真要收口只有一条路：控制台重置两个账号的口令，然后更新两个 env 文件
  （口令让控制台只生成字母数字，避开 URL 编码那个坑）。
